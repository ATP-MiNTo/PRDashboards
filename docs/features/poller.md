# Poller and snapshot

Status: Built. PRD: [PRD.md](../PRD.md). Spec: [TECH_SPEC.md](../TECH_SPEC.md) sections 9, 10 and 11.2. Related: [status-sync-rules.md](status-sync-rules.md), [command-table.md](command-table.md), [ticket-linking.md](ticket-linking.md), [stacked-prs.md](stacked-prs.md), [storage.md](storage.md), [auth.md](auth.md).

## Purpose

Refreshes the list of open pull requests assigned to the user or opened by the user from GitHub and the tickets from Jira,
builds one immutable snapshot, stores it and tells the browser. One refresh runs at a time, and a
Sync click during a refresh joins it. Browser tabs never cause outside calls.

Differences from the spec:

- After the fetch steps a refresh evaluates the status sync rules from the data it has and moves the tickets that fire ([status-sync-rules.md](status-sync-rules.md)). The result is part of the refresh transaction. A rules change evaluates again from cached data (`Reevaluate`, same as `Relink`).
- The stream carries `snapshot`, `sync-status` and `activity` (rule moves and merges).

## Data model

- API schemas: `Snapshot`, `SnapshotPr` (with `approvals`, see below), `SnapshotRepo`, `Ci`, `Check`, `Review`, `StackInfo`, `SnapshotTicket` (with `waiting` and `mergePlan`), `Sources`, `SourceStatus`, `RateLimitUsage`, `BlockedOrg`, `Warning`, `SyncStatus` in [api/openapi.yaml](../../api/openapi.yaml). `version` is an integer that grows with every build of the snapshot and continues after a restart.
- `SnapshotPr.roles` says why a PR is listed: `assigned` when the assigned search returned it, `authored` when the authored search did, both when both did (never empty). `SearchOpen` sets `github.PR.Roles` while it merges the two result sets by PR id, and `build` maps it (`rolesOf`). Roles live in the snapshot JSON only, not in a SQLite column, so there is no migration. A snapshot stored before roles existed has none: `Load` gives such a PR both roles (`fillRoles`) and re-encodes the JSON it serves, so the UI still shows it. The next refresh replaces them with the real ones.
- `SnapshotPr.author`, `updatedAt`, `additions` and `deletions` feed the cards of [command-table.md](command-table.md): who opened the pull request (the login, null for a deleted account), when it last changed on GitHub and the lines of its diff. They are fields of the same two searches (`author { login }`, `updatedAt`, `additions`, `deletions` in the `PullRequestFields` fragment), so there is no extra call. `build` copies them (`Additions` and `Deletions` are always set by a refresh, even 0). Like roles they live in the snapshot JSON only. A snapshot stored before they existed decodes them as nil, and `Load` re-encodes it, so they are served as `null` until the next refresh; the UI shows no author, no update time and no diff for such a card.
- `SnapshotPr.approvals {have, need, changesRequested}` is computed by `build` from the reviews the two searches already return (`latestReviews`, one per reviewer) and the repo's `approvals_required` (`merge.CountApprovals`, pure; `newRepo` gives a repo the store has not seen the default of 1). It adds no call. A snapshot stored before it existed gets it from its stored reviews and the stored setting in `Load` (`fillApprovals`). The merge flow reads the same number (`Linked.ApprovalsRequired`) and refuses with "Needs N approvals, has M" ([review-actions.md](review-actions.md)).
- `Sources.github.rateLimit {used, limit, resetAt}` (`RateLimitUsage`, optional) is the GitHub GraphQL budget the last refresh saw, for the API usage text in the sidebar ([sidebar-shell.md](sidebar-shell.md)). It comes from the `rateLimit` field of the two searches (`github.RateLimit`, merged by `mergeRateLimit`), so it adds no call. `build` maps it with `rateLimitUsage` (`used` is `limit - remaining`, kept between 0 and `limit`; `resetAt` is null when GitHub gave none; the whole field is absent when GitHub reported no limit). `refresh` keeps it in `Poller.rl`, a failed fetch keeps the last known budget, and a missing, rejected or reconnect-needed token clears it. Only the github source has it. `Load` takes it back from the stored snapshot (`rateLimitOf`), so a restart shows it and still slows down on a low budget before the first refresh. A snapshot stored before it existed has none and loads as before. It lives in the snapshot JSON only, so there is no migration.
- `snapshot` table: one row (`id = 1`) with `version`, gzip-compressed JSON `data` and `updated_at`.
- `repos` (`is_new` until the user has seen the repo), `repo_branch_rules` (seeded `main` and `production` to `merge`), `prs` (`state` open, merged or closed, `last_seen_at`) and `ticket_links` are written by one transaction per refresh ([storage.md](storage.md)). New repos get the global default method. The refresh reads the stored repo configuration (`Store.Repos`) so `build` can resolve `SnapshotPr.mergeMethod` ([merge-method.md](merge-method.md)). `Linked` and `Refs` give the merge flow the ticket keys and the head and base branches of the open PRs from the current snapshot.
- Settings read: `polling.githubSec`, `polling.jiraSec` (re-read before every wait, so a change applies without a restart). Each is a multiple of 15 from 30 to 3600 ([settings.md](settings.md)); `Interval` and `plan` raise anything below `MinInterval` (30 s, a hand-edited database) to it.

## Key flows

1. Start: `Load` restores the stored snapshot (a corrupt one is ignored), then `Run` refreshes at once.
2. `Run` reads the settings, `plan` computes when GitHub and Jira are due (interval, doubled while the rate limit is low, or the backoff, whichever is later), runs a refresh when due and otherwise waits for the timer or `Reschedule`.
3. `refresh`: GitHub searches (`SearchOpen`: assigned and authored, in parallel, merged by PR id), merged searches when PRs left, user links, Jira site, project keys, ticket lookup, repo states, `runRules`, `build`, encode and compress, `SaveRefresh` (one transaction), publish `snapshot` then `sync-status`.
4. A fetch failure never fails the refresh. GitHub rate limits (`403` or `429` with `Retry-After` or `x-ratelimit-reset`, and a `403` whose body names a secondary rate limit, which backs off exponentially from 2 s up to 5 min) and errors keep the last list and record `rate_limited` or `error` with `resetAt`. The web shows the state in the popover of the Refresh button in the header ([header.md](header.md)), a banner with the age of the data and a "Last data" mark on every row ([command-table.md](command-table.md)). A rejected token, a GitHub App connection that needs a reconnect (error text "Reconnect GitHub") or a missing connection clears the list and records `disconnected`. Jira failures mark rows `ticketLookup: unreachable` and keep the last tickets.
5. Sync button: `POST /api/sync` calls `Trigger` (202, joins the running refresh). Connecting or disconnecting an account and changing the Jira site also call `Trigger`. Saving settings calls `Reschedule`.
6. Manual link changes: `PUT /api/prs/{id}/tickets` stores them and `Relink` rebuilds the snapshot from memory, asking Jira only for keys it has not seen ([ticket-linking.md](ticket-linking.md)).
7. Browser: `GET /api/snapshot` with `If-None-Match` answers `304` when the version is unchanged. `GET /events` streams `snapshot {version}` and `sync-status {running, githubAt, jiraAt, nextGithubAt, nextJiraAt, refreshes, snapshotVersion, rateLimit}`.
8. A refresh that changes nothing the person sees keeps the version. After `build` the poller hashes the snapshot as canonical JSON with `version`, `generatedAt`, `sources.*.syncedAt` and `sources.github.rateLimit` left out (`fingerprint`, kept in the poller, also computed by `Load`). When the hash equals the last one the poller keeps the published snapshot and its version, writes no snapshot blob (`Refresh.Snapshot` empty: `SaveRefresh` and `SaveSync` leave the stored row alone, and the refresh that fetched GitHub still stores the pull requests, links and resolutions) and publishes no `snapshot` event. `sync-status` is still published when the refresh ends, with `refreshes` (finished refreshes, always up), `snapshotVersion` and the `rateLimit` of the latest refresh, so "last synced" and the API usage stay fresh; the web reads them from there (the snapshot copy of the sync times and the usage is as old as the last change). After a restart the stored sync times are those of the last change, so the first refresh may come sooner. The Refresh button uses `refreshes` and `snapshotVersion` to toast "Nothing changed" for a refresh that kept the version.
9. The poller keeps the snapshot gzip it already computes for the store in `Published.Gzip` (`Load` compresses the JSON it serves, as the stored blob predates the filled fields). `GET /api/snapshot` sends it with `Content-Encoding: gzip` when `Accept-Encoding` allows gzip (not `q=0`), otherwise the JSON, always with `Vary: Accept-Encoding`. Both forms and the 304 carry the same version ETag. A request costs no encoding and no compression.
10. After a merge, a review or a retry the services call `TriggerAfterAction(keys)`, not `Trigger`: GitHub is searched only when it is not in backoff (`ghBackoff`, the same test `plan` uses), and Jira is asked only for the given keys that the snapshot shows (the tickets the merge or retry moved, none for a review), without the project list. Keys of an action that joins a running refresh are added to it. The person's Sync (`Trigger`) and an account or Jira-site change still ask both sources and ignore the backoff. Single flight is unchanged.

## Outside calls

Per refresh, independent of the number of PRs:

- GitHub: two GraphQL searches, `assignee:@me` and `author:@me`, run concurrently (two requests in flight) and merged by PR id in one in-memory pass (the roles come from which search returned the PR), so a PR that is both assigned and authored is one row with both roles and no extra GitHub call. Each search is one request per 50 PRs (120 PRs found by both are 6 requests). Plus two merged searches (`assignee:@me` and `author:@me`, also concurrent) only when PRs left the open list. The same query returns the per-check CI. `Capped` is set when either search is capped, and `Total` is the larger of the unique PRs returned and the biggest count GitHub reported. If either search fails on its first page the whole GitHub fetch fails with that error (a rejected token first, then a rate limit, then any other). Rate limit: costs add up, the remaining budget is the lowest one seen.
- Jira (on the Jira interval): one project search page per 50 projects, one JQL per 100 ticket keys (120 keys are 2 requests). Between Jira intervals only keys not looked up before are asked.
- Rule firings add one transitions lookup (cached 60 s) and one move per ticket that fires, nothing else.
- Polling every 30 seconds is safe for the budget and the limits: one refresh is two searches (about 1 point per 50 pull requests each, so a hundred pull requests cost a few hundred points an hour at 30 s), the interval doubles while less than a tenth of the limit is left, a rate limit answer (`Retry-After`, `x-ratelimit-reset` or a secondary limit body) pushes the next refresh to its reset or an exponential backoff (`ghBackoff`, in `plan`, whichever is later), and `Sync`, `Trigger` and the review and merge refreshes join the running refresh, so shorter intervals never run two at once.
- Backoff: GitHub rate limits wait for `Retry-After` or `resetAt`, other errors use `internal/backoff`. Jira honours `Retry-After` on `429` and `503`.

## Rules and invariants

- Lifecycle: `New` creates the base context of every refresh, so `Sync`, `Trigger` and `Relink` work before `Run`. When `Run`'s context ends it cancels that context, refuses new refreshes (a flight that is already done with `context.Canceled`; a later `Run` starts afresh) and returns only after the running refresh goroutine has finished (a `sync.WaitGroup`), so nothing touches the database after the server closes it.

- One refresh at a time. `Sync` and `Trigger` join the running one. `Relink` waits for it.
- Exactly one store transaction per refresh that fetched GitHub data, including the rule activity, firings and retries. A refresh without a GitHub fetch writes the snapshot row, and the rule result when there is one. A refresh that left the snapshot unchanged writes no snapshot row.
- The snapshot is immutable once published. `Current` returns an atomic pointer, and `Published.JSON` is encoded once and served as is.
- Fine-grained tokens cannot read check runs through GraphQL: GitHub answers `FORBIDDEN` ("Resource not accessible by personal access token", `saml_failure` and `ip_allow_list_failure` false) once per check, with a path through `statusCheckRollup` and `contexts`, and returns null context nodes, but still sends the rollup state and `totalCount`. This is a known limitation, not an error: the github package drops these errors (`hiddenCheckError`), so `SearchResult.Errors` stays empty, no `github_partial` warning and no organization banner are shown, and merged-PR resolution is unaffected. The pull request is kept and the CI column shows only the overall state and "N checks" linking to GitHub's checks page. The log gets one DEBUG line per page ("github hid check runs from this token", with a count) instead of one WARN per check. A `FORBIDDEN` error elsewhere, or with an SSO or policy flag, is still reported or blocked as before. The `saml_failure` and `ip_allow_list_failure` flags of an error decide SSO or policy blocks before any wording is guessed.
- PRs that left the list are resolved only from a complete search: not capped, not partial, no GraphQL errors (other than the hidden check runs above) and no blocked organization. Otherwise they stay open.
- Tokens never enter the snapshot, the log or an event. Errors in the snapshot are fixed, user-facing texts.
- The SSE hub keeps the last event per name, replays it to a new client, drops a client whose buffer is full and sets a write deadline per write. `WriteTimeout` of the HTTP server stays unset.
- `go test -race` covers the single flight with concurrent `Sync` calls (exactly one outbound refresh).
