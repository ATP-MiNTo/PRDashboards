# Status sync rules and Multi-PR tickets

Status: Built. PRD: [PRD.md](../PRD.md). Spec: [TECH_SPEC.md](../TECH_SPEC.md) sections 7.3, 7.4, 7.5 and 7.7. Related: [poller.md](poller.md), [merge-and-transition.md](merge-and-transition.md), [settings.md](settings.md), [ticket-linking.md](ticket-linking.md), [storage.md](storage.md).

## Purpose

One ordered list of rules keeps Jira tickets in the right status during the life of their pull
requests, including at merge. A rule is "when `<trigger>` and `<filters>` then move the ticket to
`<status>`" with a mode, All or Any, for tickets that have several pull requests. A rule fires once
per change, so a manual move in Jira is not undone until something new happens.

Differences from the spec:

- Merged pull requests count for `merged` rules and for the set of a mode All rule only inside a 30 day window (`mergedWindow`). A merged pull request is ignored by every other trigger, and a closed one never counts.
- `ready_for_review` uses `prs.ready_sha`, the head SHA when the PR last became ready. A push keeps it, going back to draft clears it.
- A rule whose target status has no transition from the ticket's current status is recorded once as `skipped` and not retried. A failed lookup of the transitions records nothing, so the next refresh retries.
- A transition with required fields is not sent. It is recorded as `needs_input` and shown in the Activity list, because nobody is there to fill the fields.
- Changing a rule's mode saves with the baseline, so nothing moves because of the change.
- Two triggers go beyond the spec's list. `no_review_yet` holds for an open pull request that is not a draft, has a head SHA, no review submitted and no review decision (or `REVIEW_REQUIRED`), and fires once per head commit (fingerprint `<headSha>:unreviewed`). `waiting_approvals` holds for an open, non-draft pull request with a head SHA whose approvals are at least 1 and below the approvals required, and fires once per head commit (`<headSha>:waiting`). The approvals required are the per-repo setting of [merge-and-transition.md](merge-and-transition.md), read by `store.SyncState` (`ApprovalsNeed`), counted with `merge.CountApprovals` by the poller and passed in through `rules.PR.ApprovalsHave` and `ApprovalsNeed`, so the engine stays pure. A repo with no requirement (0) never matches. Old stored rules still load, since the enum only grew.
- The prototype's multi-valued rule (several triggers, several values per filter, "Ask first", "Only move forward", "Tickets in the same PR", a commit-age condition) is not in the engine. The dialog keeps one trigger, one value per filter and the two Multi-PR modes, and nothing else is invented.
- Preview and baseline use the cached snapshot data and make no outside call.
- A ticket whose current status is one of `Settings.excludedStatuses` (default `Done`, compared by `rules.StatusKey`: without regard to case, spaces and punctuation, so "Re-open", "re open" and "REOPEN" are one status while "Reopened" is another) is never moved, fired or listed as waiting by any rule, and has no merge plan. Evaluate, preview, baseline and the merge plan all skip it, so a ticket in an excluded status that matches a rule's target is not even recorded as already there.

## Data model

- `sync_rules` (`id`, `position`, `name`, `enabled`, `trigger`, `filters` JSON, `target_status`, `mode`) and `rule_firings` (`rule_id`, `ticket_key`, `fingerprint`, `fired_at`, deleted with the rule) ([storage.md](storage.md)). Migration `0003_sync.sql` adds `prs.ready_sha`.
- API schemas in [api/openapi.yaml](../../api/openapi.yaml): `SyncRule`, `RuleTrigger`, `RuleMode`, `RuleFilters`, `Rules`, `RulesUpdate` (`rules`, `baseline`), `RulePreviewRequest`, `RulePreview`, `RuleMove`, `RuleWaiting`, `PrRef`, `TicketWaiting`, `TicketMergePlan` and `JiraOptions` (`statuses`, `projects`). `Settings.excludedStatuses` holds the excluded statuses (at most 50, each 1 to 100 characters, stored under the `excludedStatuses` settings key, default `["Done"]`). `SnapshotTicket` has `waiting` and `mergePlan`, both nullable.
- Activity rows of a rule have `triggered_by = "rule:<id>"` and the result `ok`, `failed`, `skipped` or `needs_input`. A failed move adds a `pending_retries` row without a PR.
- Limits: at most 100 rules, `commit_stale` hours 1 to 720, names, statuses and issue types up to 100 characters, repo and branch globs up to 200 characters of letters, digits and `. _ / * -`, a Jira project of letters, digits and `_`. Triggers and modes are strict enums.

## Key flows

1. After each refresh, `runRules` reads the stored firings (`SyncState`), builds one `rules.Input` from the open pull requests, the merged ones of the last 30 days, the fetched tickets and `Settings.excludedStatuses`, and calls `rules.Evaluate`. Changing the excluded statuses evaluates again from cached data. The rules are walked in order, the first enabled rule that holds and whose fingerprint differs from the stored one fires, at most one per ticket.
2. Each trigger has its fingerprint from the spec table. Mode All fingerprints the whole set, `sorted(prID=fingerprint)` joined by commas, so it fires once, when the last pull request meets the rule. Mode Any fires for the first pull request that meets it. Unavailable data (no CI result, no head SHA, Jira data missing) never matches.
3. A ticket already in the target status records the firing and sends nothing. Otherwise `fire` fetches the transitions of that ticket (60 s cache), picks the one whose `to` name equals the target ignoring case, and posts it. At most 4 tickets run in parallel.
4. The activity rows, the `rule_firings` and the retries of one refresh are written in the same transaction as the snapshot (`SaveRefresh`). Then the `activity` and `snapshot` events are published.
5. Saving the list (`PUT /api/rules` with `{rules, baseline}`) replaces it in one transaction. A rule is changed when it is new or its enabled flag, trigger, hours, filters, target or mode differ (the name does not count). Changed rules lose their firings. With `baseline: true` the current holds of the changed rules are stored in the same transaction, so existing tickets do not move. Then `Reevaluate` runs from cached data and moves tickets whose rule now fires.
6. `POST /api/rules/preview` evaluates one rule against the cached data and answers the tickets it would move now, the ones already in the target status and the ones waiting. A card whose rule has a change that can move tickets needs a preview of the rule as it stands before Save rule is possible, and offers "Move them" or "Don't move existing tickets" (the baseline) when something would move.
7. Merge dialog: `mergePlan` (`rules.AfterMerge`) says what the first matching `merged` rule does once this pull request is merged. The dialog preselects that transition when it is loaded ("Jira INP-1 moves to [Ready to Merge]"), and the person still confirms it. When other pull requests must merge first (mode All) it shows "Won't move yet: waiting on ..." and defaults to "Leave as <status>". The status dropdown can still move the ticket. The merge flow records the `merged` fingerprints with the just merged pull request counted as merged, so the engine does not fire again.
8. The dialog. The sidebar button "Status sync rules" (Settings sidebar) opens a wide modal ([dialog-and-popover.md](dialog-and-popover.md), `Modal wide`, the focus returns to the button). It holds, top to bottom: the title with an "i" note ([InfoTip](../../web/src/components/InfoTip/InfoTip.tsx), also the description of the button), the rule cards, "Add rule" and "Preview", the Preview panel, Exclude statuses and Activity. Each card is a list item named "Rule N, <name>": grip, number badge, name (a ghost input), Mode select (Auto or Off, the same flag as the switch), the enable switch, trash and a chevron that folds the body (0.3 s). Rules are folded when the dialog opens. The body has one field per part of the rule: "When this happens to the PR" (the trigger as a chip, changed with the "When" select, plus "Hours" for `commit_stale`), the filters as chip fields ("On branches", "In repositories", "In Jira projects", "If the ticket is in", "Of issue type": "Any" when empty, one removable chip when set, and a "+ Add" select or a text field with suggestions), "Then move it to" (a select of the Jira statuses) and "Tickets shared by several PRs" (the rule's mode, All or Any, with the TECH_SPEC 7.5 sentence as its description).
   - Immediate saves, each one `PUT /api/rules` with the whole list: reordering, deleting, turning a rule off and changing the mode of an otherwise unchanged rule (with `baseline: true`). Everything else is an edit of the card, shown with an "Unsaved" badge and a bar with Preview, Save rule and Cancel. A name-only edit needs no preview. Turning a rule on is an edit too, so it goes through its preview. A new card is not saved until Save rule, and Cancel or its trash forgets it. The edits of one card survive the reorder of another.
   - Reordering: the grip drags the card (HTML drag and drop, the card is made draggable on `mousedown` of the grip), a drop line shows where it lands (`dropSlot`, `dropLineY`) and the list scrolls near its edges. Keyboard: each card has "Move <name> up" and "Move <name> down" buttons that are visible only when focused, and the focus stays on the one that was used. A move saves the whole list at once (`reorder`).
   - "Add rule" opens a menu of templates (`RULE_TEMPLATES`): one per trigger, including "No review yet" and "Waiting for more approvals", and a blank rule. A template's target is kept only when Jira lists the status (by `statusKey`), otherwise it is left empty for the person to pick (when Jira lists nothing the suggestion stays). The new card opens with its name selected.
   - "Preview" shows the Preview panel. "Right now": one `POST /api/rules/preview` per enabled rule that has no problem (`usePreviewRules`, 250 ms after the last edit, a rename asks nothing), combined by `previewTable` into one table (Ticket, When, Moves, Because; the first rule that would move a ticket wins, as in the engine) and a "Won't move (n)" list with the reasons (already in the target status, waiting on k of n PRs). "If merged": built by `mergeTable` from the `mergePlan` of the snapshot tickets, so it shows the saved rules only and says so while there are unsaved edits. No new endpoint is used.
   - Exclude statuses (chips, "Tickets in these statuses are never moved.", a "+ Add" select of the Jira statuses, at most 50, near-duplicates by `statusKey` listed once, an excluded status that Jira does not list stays) and the Activity list (moved here from the sidebar, with the retries and "Load more") live in the dialog. The sidebar keeps polling, Delete branch after merge, Sessions and Theme.
9. Rule form and Exclude statuses (web). `GET /api/jira/options` returns `{statuses, projects}`. The statuses come from one cached Jira call, the projects from the keys of the last full Jira refresh held in memory (no call). If Jira is not connected it answers `409 not_connected`. If the statuses call fails for another reason it still answers `200` with the projects and an empty `statuses`, and logs the failure. The web reads it only once the rules dialog opens, never while it is closed (`useJiraOptions`, stale after 5 minutes, no refetch on focus or on a timer). The "Then move it to" select lists the statuses, and the "If the ticket is in" and "In Jira projects" chip fields offer the statuses and the project keys. Each also keeps its current value when Jira does not list it, so a saved rule still shows. When a list is empty or the request failed, the dialog uses the statuses (`statusesOf`) and the project prefixes (`projectsOf`) of the snapshot. Repository, branch and issue type are typed, with the repositories and branches of the pull requests as suggestions for the first two.
10. A ticket whose All rule waits (some pull requests meet it, others do not, and the ticket is not in the target status) shows "Waiting on 2 of 3 PRs: FE #34, proxy #56" in the ticket cell.

## Outside calls

- Evaluating, previewing and the baseline make none.
- `GET /api/jira/options` costs at most one `GET /rest/api/3/status` per site every 10 minutes. It makes no GitHub call.
- A firing ticket that is not yet in the target status costs one `GET /rest/api/3/issue/{key}/transitions?expand=transitions.fields` (cached 60 s) and, when a transition matches without required fields, one `POST` to move it. Tickets that do not fire and tickets already in the target status cost nothing.
- Opening the merge dialog for a ticket with a merge plan that is not waiting fetches its transitions (cached).

## Rules and invariants

- `internal/rules` is pure: no network, database or clock (the time is an input).
- A rule fires only when the fingerprint differs from the stored one, so restarts catch up on what happened while the app was closed and a manual move is not undone.
- At most one transition per ticket per evaluation, and the first matching enabled rule wins.
- Every move re-checks the transitions from Jira before it is sent. A deleted rule's firings are dropped by the store (the insert joins `sync_rules`).
- The list is written whole in one transaction, no per-row loops. The browser never triggers an outside call by saving rules.
- The hint of the "Tickets shared by several PRs" select is the sentence of TECH_SPEC 7.5 (`MULTI_PR_HINT`), shown as a tooltip and as the accessible description of the select.
