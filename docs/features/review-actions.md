# Review actions and approvals

Status: Built. PRD: [PRD.md](../PRD.md). Spec: [TECH_SPEC.md](../TECH_SPEC.md) sections 7.7, 8 and 9. Related: [merge-and-transition.md](merge-and-transition.md), [settings.md](settings.md), [poller.md](poller.md), [security.md](security.md), [auth.md](auth.md), [command-table.md](command-table.md).

## Purpose

Lets the person approve a pull request, request changes on it and take a draft out of draft from the
dashboard, and makes the number of approvals a repository requires part of the merge rules. The
server side, the web plumbing (API client functions and mutation hooks) and the controls on the
cards are built here: the Review badge with its Action menu (Approve, Request change), the dialog
that asks for the text of a request for changes, and the Ready button of a draft. The rest of the
card is in [command-table.md](command-table.md).

Differences from the spec: this is not in the PRD or the spec. It follows the pattern of the merge
([merge-and-transition.md](merge-and-transition.md)): the browser asks, the server checks again
against fresh data and acts as the viewer.

## Data model

- API: `POST /api/prs/{id}/approve` (`ApproveRequest {expectedHeadSha, body?}`), `POST /api/prs/{id}/request-changes` (`RequestChangesRequest {expectedHeadSha, body}`, `body` 1 to 65536 characters and not only white space) and `POST /api/prs/{id}/ready` (`ReadyRequest {expectedHeadSha}`) answer `ReviewResult {prId, action: approve | request_changes | ready}`. `expectedHeadSha` is 7 to 64 hex characters, the head the card showed. GitHub's limit for a review text is 65536 characters; the 64 KiB request cap ([security.md](security.md)) is checked first, so the largest text that arrives is a little shorter.
- Refusals: 409 `ReviewConflict` (a `MergeProblem`, with the fresh pull request in `pr`): `not_open`, `head_moved`, `not_draft`, `own_pull_request`, `not_connected`. 404 `not_found`. 422 `body_required` (white space only) and `review_rejected` (GitHub refused for another reason; the detail is "GitHub refused it: <GitHub's text, 200 characters>"). 403 `missing_permission` and `org_blocked`, 429 `rate_limited`, 502 `upstream_error`.
- Settings: `RepoSettings.approvalsRequired` (0 to 10, `ApprovalsRequired`; 0, nothing required, is the default), `RepoUpdate.approvalsRequired` (optional: left out, the stored value stays; 0 is a value of its own, so the store takes a pointer, `store.RepoUpdate.Approvals *int`, nil meaning left out). The column is `repos.approvals_required INTEGER NOT NULL DEFAULT 0 CHECK (BETWEEN 0 AND 10)`: [migration 0004](../../server/internal/store/migrations/0004_approvals.sql) added it with a default of 1 and [migration 0007](../../server/internal/store/migrations/0007_approvals_zero.sql) rebuilt the table with the new range and default and turned every stored 1 into 0 (1 was only ever the default; 2 to 10 were choices and stay). It is per repository only, not per target branch. [storage.md](storage.md), [settings.md](settings.md).
- Snapshot: `SnapshotPr.approvals {have, need, changesRequested}`. `have` is the number of distinct reviewers whose latest review is `APPROVED`, `changesRequested` the number whose latest review is `CHANGES_REQUESTED`, `need` the repo setting, 0 when it requires none. Always present. A stored snapshot gets it recomputed from its stored reviews and the current setting when it is loaded (`fillApprovals`), until the next refresh. It does so for every pull request, because 0 is a real value of `need` and can no longer stand for "not filled in yet"; that also corrects a snapshot stored before migration 0007 turned the old default of 1 into 0.

## Key flows

1. The card sends the action with the head SHA it shows (and the text, for a request for changes). The router has already applied the checks of [security.md](security.md): Host, Origin, Sec-Fetch-Site, session, CSRF, content type, body size and schema.
2. `Service.run`: the pull request must be in the current snapshot (`not_found` otherwise), the GitHub token is read (`not_connected`), and one GraphQL node query fetches the pull request again.
3. `check` against the fresh data: open (`not_open`), a draft when marking ready (`not_draft`), head equal to `expectedHeadSha` (`head_moved`), and for approve and request changes not opened by the connected user (`own_pull_request`, compared case-insensitively with the stored login of the account; GitHub refuses it too, and that refusal is mapped to the same code). A refusal carries the fresh state, and starts a refresh so the card catches up.
4. The write: approve and request changes are `POST /repos/{o}/{r}/pulls/{n}/reviews` with the event, the text and `commit_id` set to `expectedHeadSha`, so GitHub itself refuses a commit that is no longer the head (`head_moved`). Mark ready is the GraphQL mutation `markPullRequestReadyForReview` and succeeds only when GitHub answers with the pull request no longer a draft. The viewer's own token is used.
5. After a success `Refresh` starts one refresh (`Poller.Trigger`, joining a running one), the same call a merge makes. It is the usual three searches, so there is no call per pull request and no polling of its own; the `snapshot` event it publishes is what the browser already listens to. The web hooks also invalidate the snapshot query when the request ends, whatever the outcome.
6. Merge: `check` counts the approvals of the fresh pull request against `Linked.ApprovalsRequired`. The card's Merge cell uses `blockOf`, which applies the same rule to `SnapshotPr.approvals` with the same words, after "Changes requested" and before "Review required".

### On the card

1. The Review cell shows one of two things (`reviewAccess`). For a pull request the viewer can review it is the "Action" button, a primary outline badge with a chevron and a slow pulse (`rvPulse`, 2.4 s, off under reduced motion), described for assistive technology by the state sentence. Hover or click opens a menu with "Approve" (a green check) and "Request change" (a red mark). For every other pull request it is the state badge, with no button.
2. No Action for: a pull request the viewer opened (the `authored` role, or the author equals the connected login; the tooltip says "You opened this pull request, so you cannot review it."), a draft ("A draft is reviewed after it is marked ready."), and one the viewer already approved or asked changes on (the state is shown, "You approved." or "You requested changes." leads the tooltip). The login comes from `useAccounts`.
3. The state badge (`reviewBadge`, 6.1 rem by 1.75 rem) reads "Approve" (all needed approvals), "Approve 1/2", "Waiting" or "Waiting 0/2" (nothing yet) and "Change" or "Change 1/2" (changes requested wins over the rest). The fraction shows only when the repository needs more than one approval. A repository that needs none (0) says what the reviewers did and never mentions a requirement: "Approve" ("1 reviewer approved."), "Change" ("1 reviewer requested changes.") or "Waiting" ("No review yet."), with no fraction and no "needs 0 approvals" text, and the Merge cell never blocks on approvals. Otherwise the tooltip reads "1 of 2 reviewers approved. This repo needs 2 approvals to merge.", "Waiting on 1 reviewer. ...", "All 1 reviewer approved. ..." or "1 of 2 requested changes. ...", and is also in the DOM as hidden text.
4. Approve sends `useApprove` with `expectedHeadSha` set to the card's head, and shows the toast "You approved #N". It disables the Action button while the request is out.
5. Request change opens `RequestChangesDialog`: a modal "Request changes on <repo> #N" with the pull request title, a required textarea ("Comment (required)") and the buttons Cancel and "Request changes". An empty or white-space comment is refused in the browser with the same words as `body_required` ("Write a comment first. GitHub needs one to request changes.") and sends nothing. Success closes the dialog and toasts "You requested changes on #N". A refusal stays inside the dialog as an alert and keeps the text.
6. Every refusal is worded by `describeReviewProblem`, as a toast for approve and Ready and inline for the dialog: `head_moved` ("The pull request changed since the page loaded. The card was refreshed. Look at it and try again."), `not_open`, `not_draft`, `own_pull_request`, `not_connected`, `body_required`, `review_rejected` (shows GitHub's detail as text), `missing_permission` (shows the detail, which names the permission), `org_blocked`, `rate_limited`, `upstream_error`; anything else is "Something went wrong. Try again.".
6a. Up front, Ready is the only review action gated by the account's role: when the repository's `viewerPermission` is `READ` or `TRIAGE` and the viewer did not open the draft (`readyBlockOf`: the `authored` role, or `author` equal to the connected login from `useAccounts().data.github.login`, ignoring case), the button is a disabled Ready with the tooltip and description "Read-only here: your token's account can't write to <owner/repo>" and sends nothing. GitHub lets the author of a pull request mark it ready without write access. Merge is blocked the same way in `blockOf` ([merge-and-transition.md](merge-and-transition.md)). Approve and Request changes are NOT gated by the role: reviewing needs only read access on a public repository, and the token's permission cannot be predicted, so they stay available and report a refusal with the `missing_permission` detail above. `viewerPermission` is the account's role, not the token's permissions.
7. A draft shows the Ready button (the light green `btn-ready`, tooltip "Draft. Mark ready for review to merge.") in place of Merge. It sends `useMarkReady` with the head, toasts "#N is no longer a draft", and the button becomes a frosted disabled Merge with a one-pass frost sweep (1.2 s) and the tooltip "Checks restart after leaving draft." It stays a disabled Merge for up to 30 s if the snapshot still says draft, then goes back to Ready.

## Outside calls

- Per action: one GraphQL node query (the re-check) and one write: one REST review POST, or one GraphQL mutation. Then one refresh (three searches, [poller.md](poller.md)).
- Nothing from the browser to GitHub. Saving the approvals setting makes no outside call: it rebuilds the snapshot from cached data (`Relink`).

## Rules and invariants

- Every write re-checks fresh state on the server; the client's view is only an expectation (the head SHA). The head SHA is also sent to GitHub as `commit_id`.
- Permission errors name the repository and the permission: a 403 that is not SSO or an organization policy is `missing_permission`. The review service records the repository on the error (`github.WithRepo`), so the detail reads "This token can't write to acme/web: it needs the GitHub permission pull_requests: write. A fine-grained token works for one owner only, so a repository of another owner needs a token from that owner." A fine-grained token belongs to one user or organization: for a repository of another owner (public or not) adding the permission does not help, which is why the sentence says so. GitHub's `X-Accepted-GitHub-Permissions` header is used when it comes; the GraphQL mutation and a REST answer without the header get `pull_requests=write` filled in (`needsReviewPermission`). A fine-grained token needs Pull requests: write; a GitHub App needs the same ([auth.md](auth.md)). GitHub's own text is kept in the log, not in the detail.
- No idempotency key: an approval repeated is harmless (the latest review of a reviewer is what counts), and a repeated request for changes is a second review by the same reviewer, which GitHub folds into the first.
- Approvals count only the latest review of each reviewer that GitHub returns in `latestReviews(first: 10)`. A reviewer whose latest review is a comment is not counted, and only the 10 most recent reviewers are seen, which is the most `approvalsRequired` can be.
- `merge.CountApprovals`, `Approvals.Block` and `NeedOf` stay pure and are covered at 90 % or more (`pnpm coverage-check`).
- The review actions are logged at INFO (`review action done`: pull request and action, no text); no activity row is written.
- The CI "cold restart" of the design is a UI-only notion; nothing here touches CI.
