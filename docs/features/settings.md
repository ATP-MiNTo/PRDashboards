## Purpose

The Settings content, shown in the left sidebar ([sidebar-shell.md](sidebar-shell.md)) and toggled by the burger in the header ([header.md](header.md)), as the design draws it: the Repositories block, GitHub and Jira polling, and the "Status sync rules" button. There is no Theme block: the theme is the sun and moon button of the header ([theme.md](theme.md)). The accounts block is pinned at the bottom of the sidebar, with the GitHub API usage text of the last refresh in its eyebrow row ([sidebar-shell.md](sidebar-shell.md), [poller.md](poller.md)); the polling intervals above it are what keep that budget safe. Three things open in their own dialogs, all built on the shared [Modal](dialog-and-popover.md): the settings of one repository (the gear of its row), the status sync rules ([status-sync-rules.md](status-sync-rules.md)) and the accounts, opened by "Manage accounts" ([auth.md](auth.md)).

Differences from the design and the earlier UI:

- The design moves "Delete branch after merge" into the repository dialog. It is there as a per-repository choice with "Use default", and the global default it falls back to stays in the Repositories block (a small roll, "No" or "Yes", and a "Default merge method" select), because without it "Use default" would have nothing to follow. The block also has the design's third default, a "Multi-PR tickets move when" select ("All PRs are merged" or "First PR is merged"), which the rules in mode Default follow ([status-sync-rules.md](status-sync-rules.md)).
- Sessions ("Sign out all browsers") moved into the Accounts dialog (Browsers, "Sign out everywhere"). The per-rule Multi-PR mode, Exclude statuses and the activity log are in the rules dialog.
- The old per-repo accordion with Save and Save all is gone: the repository dialog saves its own changes.
- The "API usage" line of the design is not shown: the app keeps no usage data.

## Data model

Reads and writes `Settings` (`deleteBranchAfterMerge`, `defaultMethodForNewRepos`, `multiPrTickets`, `polling`, `theme`, `excludedStatuses`) and `RepoSettings` through `GET /api/repos` and `PUT /api/repos/{id}` ([merge-method.md](merge-method.md)). `RepoSettings` has `defaultMethod`, `inheritMethod` (the repository follows the default method), `deleteBranch` (`default`, `yes` or `no`), `approvalsRequired`, `branchRules`, `isNew` and `openPrs`. `PUT /api/repos` (several repos in one request) stays in the API but the UI no longer uses it. The rules dialog reads and writes the rules, the Jira options and the activity ([status-sync-rules.md](status-sync-rules.md)); the accounts dialog calls the auth endpoints ([auth.md](auth.md)).

Browser storage ([storage.md](storage.md)): `prd-repos-off` is the JSON list of repository ids the person switched off with the checkboxes of the Repositories block; the list leaves their pull requests out (`groupsOf`, `showCounts` and `listStats` take the set as `off`). It is pruned of nothing: an id that no longer exists is harmless. The fold of the Repositories block, the unsaved repository draft, and the polling values being stepped (until their save) are component state.

Polling: `PollingSeconds` in [api/openapi.yaml](../../api/openapi.yaml) is any multiple of 15 from 30 to 3600 (a superset of the five values older versions allowed, so stored values stay valid; the schema is `integer`, `minimum: 30`, `maximum: 3600`, `multipleOf: 15`, checked by the request validator). The fields step by 15 seconds from 30 to 300 and then through 15 minutes and 1 hour (`POLLING_STEPS` and `stepPolling` in [web/src/lib/polling.ts](../../web/src/lib/polling.ts)); a value between two steps moves to the next one in the direction of the arrow. The poller never waits less than 30 seconds, whatever is stored (`poller.MinInterval`), still honours GitHub's rate limit answers and runs one refresh at a time ([poller.md](poller.md)).

Approvals required: each repository has `approvalsRequired`, 0 to 10, default 0 (nothing is required, so the review badge and the merge block stay quiet), stored in `repos.approvals_required` ([storage.md](storage.md)) and applied to every target branch of the repo. The update leaves it out to keep the stored value, so 0 is a real choice. Saving rebuilds the snapshot from cached data so `SnapshotPr.approvals.need` follows at once ([review-actions.md](review-actions.md)). The repository dialog edits it.

"Custom" repositories: the gear of a row is the blue filled gear when the repository has settings of its own (`isCustom`: a delete-branch choice, a method of its own, any approval required (1 or more), or branch rules other than the seeded ones, compared by their fields) and the outline gear when it follows the defaults.

## Key flows

1. The burger in the header opens the sidebar on the left, a column on wide screens and a modal overlay on narrow ones (focus, Tab, Escape, scrim and animation rules are in [sidebar-shell.md](sidebar-shell.md)). The dialogs open from their own buttons.
2. Repositories: the header is a disclosure button (`aria-expanded`, folded by default). A checkbox switches a repository off or on for the list (`setOff`, `prd-repos-off`); "Select all" clears the set and "Clear" switches every repository off. The count says how many are shown.
3. The gear opens the repository dialog: the title is the repository name with an info tip ("Fetched with <token name> (kind, login). Your role here: ...", or "Fetched via ..." when the snapshot has no token for it), the blue Done button is pinned at the top right. It has the "Delete branch after merge" roll and the "Merge method" roll (both the field variant of `RollSwitch`, see "The two rolls" below) and "Approvals required to merge" (a read-only spinbutton stepped by the mouse wheel (a native non-passive listener, at most one step per 120 ms), the arrow keys and the minus and plus buttons, 0 to 10, 0 for none) and "Method per target branch": one row per rule with the pattern (an input with a `datalist` of the branches the snapshot knows for that repository), the method select and a remove button, and "Add branch rule" (at most 50). The first rule that matches wins. A change is saved 500 ms after the last one (`REPO_SAVE_MS`), as one `PUT /api/repos/{id}`, and when the dialog closes; nothing is sent while a pattern is invalid (closing then drops the invalid rows). A new repository is confirmed (`clearNew: true` is always sent) when its dialog closes. A failed save says so in the dialog and is sent again with the next change.
   The two rolls ("Delete branch after merge" and "Merge method") are each in one of two states: the default ("Use default (No)", "Use default (Squash)") or an explicit value. They open in the stored state, which is the default for a repository that was never customised. A left-click, Enter or Space turns through the explicit values only and never lands on the default: Yes and No for delete branch, and Squash, Merge commit and Rebase for the method (only the methods the repository allows, in `methodChoices` order). From the default it goes to the value after the one the default stands for now (default No goes to Yes, default Squash goes to Merge commit). A right-click, Shift+click, Shift+Enter, Shift+Space or the Menu key switches the default on or off: off, it goes to the value that was remembered, which is the method the repository stores of its own (`ownMethod`) and, for delete branch, the stored choice or the last value the roll had in this dialog, else the value the default stands for now (`deleteDefaultOf`, No while the default is unknown); on, it goes back to the default. The same switch-off or switch-on moves a method that was chosen into `ownMethod` (`withMethod`), so the repository keeps it while it follows the default. A saved default is `inheritMethod: true` (or `deleteBranch: default`), an explicit value the value itself. The roll is `RollSwitch` with its optional `defaultChoice` prop ([toolbar-pager-footer.md](toolbar-pager-footer.md)); its tooltip and accessible name say "Click: next choice. Right-click, Shift+click or Shift+Enter: use default or choose". The per-branch rule method select is a plain select and is unchanged.
4. The default merge method select, the "Multi-PR tickets move when" select and the delete-branch default roll in the Repositories block save the whole `Settings` through `PUT /api/settings` (`useSaveSettings`). A changed default method makes the server relink the snapshot, because repositories that follow it resolve with it ([merge-method.md](merge-method.md)). A changed `multiPrTickets` records what holds now for the rules in mode `default` (so nothing moves) and evaluates the rules again from cached data, because the waiting hints and merge plans follow it ([status-sync-rules.md](status-sync-rules.md)); like the other settings it makes no GitHub or Jira call of its own.
5. Polling is two numeric fields ("GitHub polling" and "Jira polling", in seconds, each a `role="spinbutton"` on a read-only input). The mouse wheel and the up and down arrow keys step through the steps above. A step shows at once and is saved 500 ms after the last one, as one `PUT /api/settings`. The "Status sync rules" button under them (`aria-haspopup="dialog"`) opens the rules dialog. Theme is its own section with the Auto checkbox ([theme.md](theme.md)); light and dark are chosen in the header.
6. Status sync rules, Exclude statuses, the per-rule Multi-PR mode and the Activity list are in the rules dialog ([status-sync-rules.md](status-sync-rules.md)).

## Outside calls

The Settings content mounts when the sidebar first opens, which on a wide screen is page load, so only local calls may run then. On mount it reads `GET /api/settings`, `GET /api/repos`, `GET /api/accounts` (the VIA badge and its hint) and the snapshot from the query cache. The rules, the activity and the retries are read when the rules dialog opens; the setup state when the accounts dialog opens. These handlers read the database and make no GitHub or Jira call. `GET /api/jira/options` is the only Settings request that reaches Jira (`GET /rest/api/3/status`, cached 10 minutes on the server). The rules dialog enables it only while it is open, never on mount and never on a timer. The content stays mounted after a collapse, so unsaved drafts survive. Saving a repo makes the server rebuild the snapshot from cached data, with one Jira lookup for tickets it has not seen.

## Rules and invariants

- A dropdown that is open closes on Escape without closing the sidebar. A dialog open over the page keeps the wide sidebar from auto-collapsing ([sidebar-shell.md](sidebar-shell.md)).
- The repository dialog never sends an invalid pattern while it is open, and never loses an edit: it sends a waiting one when it closes or unmounts.
- No inline styles, no `dangerouslySetInnerHTML`.
- Rule patterns are checked in the browser and again by the server (schema pattern and length).
